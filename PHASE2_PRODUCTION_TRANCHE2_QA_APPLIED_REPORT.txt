4. WHY THE ORIGINAL AUDIT'S "METADATA-ONLY" CONCLUSION WAS WRONG
----------------------------------------------------------------------
The original consistency audit (PHASE2_PRODUCTION_TRANCHE2_CONSISTENCY_
FLAGS.txt) tested these two rows only for unhedged speculative wording
in the referent ("likely a placeholder/bounding-box technical object")
and, finding the OPAQUE/NOT_APPLICABLE classification "internally
consistent" with that wording, concluded the defect was cosmetic. It
never cross-checked the classification itself against the calibration
set's own prior resolution of the identical question for the same
naming family (Box06/BoxA1). A generic, numbered, real-object noun is
not OPAQUE merely because its exact subtype/owner/variant is
unspecified -- that is precisely what the calibration audit had already
settled for this family. This was an actual classification error
masquerading as a wording defect, not a true metadata-only case.

PHASE2_PRODUCTION_TRANCHE2_CONSISTENCY_FLAGS.txt has been updated in
place to record the corrected verdict for both rows and to state this
failure mode explicitly, rather than leaving the original
misdiagnosis unremarked. PHASE2_PRODUCTION_TRANCHE2_REPORT.txt's
tranche-only statistics have likewise been updated to the corrected
figures.

No new taxonomy rule was created or is needed: Rule 22 already
establishes that a stable core reading at the level actually specified
is CLEAR even when subtype/owner/variant is missing, and the settled
Box06/BoxA1 calibration precedent is a direct, already-existing
application of that rule to this exact family. The defect was in
applying the existing rule during the consistency audit, not a gap in
the rule itself -- so PHASE2_SEMANTIC_RULEBOOK_FINAL.txt and
PHASE2_SEMANTIC_BATCH_RULES.txt were not modified. For future
consistency audits, the required check is recorded here and in the
corrected PHASE2_PRODUCTION_TRANCHE2_CONSISTENCY_FLAGS.txt: whenever an
OPAQUE row's referent already names a real object/function/anatomical
concept, verify against accepted calibration/production precedent for
that same family before accepting OPAQUE as correct -- do not stop at
checking whether the wording is internally hedge-consistent.
