----------------------------------------------------------------------
METHOD
----------------------------------------------------------------------
For every flag, three questions were explicitly worked through rather
than defaulting to "awareness only":
  1. Does this contradict an accepted calibration or production
     precedent?
  2. Is the classification (semantic_status/taxonomy_status/
     proposed_destination) actually wrong?
  3. Is only the metadata/reason text wrong, or is the difference
     genuinely justified by the complete literals?

     as opacity, which is exactly the calibration audit's own settled
     counter-principle for this exact family. This is an actual
     classification error, not a metadata-only defect.
  3. Metadata/reason wrong? Also yes (the unhedged "likely
     placeholder/bounding-box" guess), but that is secondary to point 2.
  CORRECTED TO: CLEAR / CLEAR / groupFile/Other / High. Full field
  values and rationale in PHASE2_PRODUCTION_TRANCHE2_QA_APPLIED_REPORT.txt.

AUDIT-METHOD FAILURE MODE (recorded per external review)
----------------------------------------------------------------------
The original audit tested these two OPAQUE rows only for speculative/
unhedged wording (question 3) and, on finding the classification
"looked internally consistent" with OPAQUE's own definition, answered
question 2 ("is the classification wrong?") without actually cross-
checking the literal against the accepted calibration precedent for the
SAME coherent naming family (Box06/BoxA1 -> Other). A generic-and-
numbered object name is not automatically OPAQUE; when the calibration
set has already resolved that exact question for the same family, this
check must be performed before accepting OPAQUE as correct. See
PHASE2_PRODUCTION_TRANCHE2_QA_APPLIED_REPORT.txt Section 4 for the
narrow sweep performed to check for further instances of this failure
mode elsewhere in positions 501-2500 (none found beyond box10/box22).
